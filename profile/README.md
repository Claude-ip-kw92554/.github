<p>Claude 网页端用久了会发现一个规律：账号本身没出问题，卡的是线路。同一条出口上同时挂着几个人的会话，白天还顺，晚上八点一过就开始转圈，长回复断在半截，重发一次又是半分钟。这篇不讲结论，只记录一次能自己复现的对照实验：同一台机器、同一份操作脚本，分别放在共享线路和「一个账号一套独立指纹加静态出口」两组条件下各跑三天，把体感翻译成四个数字。做完这一轮，那笔钱该不该花你自己就能判断。</p>

<h2>一、实验怎么搭：两组之间只改一个变量</h2>
<p>对照实验最容易失败的地方是变量不干净。如果 A 组用旧笔记本、B 组换新台式机，结论就会被本机性能污染。我的做法是同一台机器、同一个 Claude 账号、同一份提示词脚本，唯一改动的是出口和浏览器配置文件：A 组走团队共用的那条线路，B 组用一条静态住宅地址，配一个独立的浏览器配置文件并由它固定出口。</p>
<p>变量清单先写在纸上。清单至少五列：出口地址、配置文件编号、系统时区与语言、并发会话数、单次观察时长。这五列钉死，后面每天的数据才有可比性。时区和语言最容易被忽略，页面上的时间显示和数字格式化都跟它有关，两组不一致能让首屏渲染差出几百毫秒，你还以为是线路的锅。</p>
<h3>操作脚本只用同一份</h3>
<p>脚本固定成三段动作：新建一个会话、发一条三百字左右的中文长问、等回复完整渲染后复制全文。三段重复二十次算一轮，两轮之间隔十分钟。别在脚本里加随机等待，加了之后延迟数据就没法横向对比，只能自己跟自己讲故事。</p>
<h3>观察窗口定在三个时段</h3>
<p>按 10:00、20:00、23:30 各跑一轮，连跑三天共九轮。只测中午会得出「两组都挺快」的错误结论，共享线路的真实差异基本集中在晚间那两个小时里。</p>

<h2>二、A 组：共享出口这三天到底卡在哪</h2>
<p>先把体感描述清楚，再谈数字。共享线路最典型的症状不是「一直慢」，而是「忽快忽慢」——同一句话发出去，有时两秒出首字，有时要等到你以为页面死掉了。这种不确定性比稳定偏慢更难忍，因为它让你没法安排工作节奏。</p>
<h3>上午时段几乎看不出差别</h3>
<p>10:00 那一轮，A 组和 B 组的首字延迟中位数只差 200 毫秒上下，肉眼分不出来。原因很直接：上午同线路的其他使用者大多在开会或写文档，出口带宽和上游连接都空着。这也说明，只看白天数据就下单的人，等于没测。</p>
<h3>晚高峰才是分水岭</h3>
<p>20:00 那一轮，A 组的首字延迟中位数跳到 3.4 秒，最长一次 11 秒；同一时段 B 组是 1.6 秒。差距的来源有两层：一是共享出口的并发会话数翻倍，请求在出口侧排队；二是同段地址在晚间被更多业务同时使用，往返时延的抖动从 30 毫秒涨到 140 毫秒。</p>
<p>断流之后的连带成本。长回复断流看着只是重发一次，实际成本是三段：等页面恢复的时间、重新组织上下文的时间、以及被截断的回答需要人再确认一遍的时间。A 组三天里出现 9 次明显断流，B 组 2 次。按每次五分钟估算，光这一项一周就是四十多分钟，账不小。</p>

<h2>三、B 组：独立指纹配静态出口的实测</h2>
<p>B 组的关键不在「住宅」两个字，而在两件事同时固定：出口地址三天没变过，浏览器配置文件里的时区、语言、字体渲染参数也三天没变过。出口和本地环境对得上，页面加载就少了那些看不见的等待。</p>

<h3>首屏和长回复要拆开看</h3>
<p>首屏主要吃往返时延，长回复主要吃连接稳定性，两者经常背离。B 组的首屏在晚高峰稳定在 1.2 至 1.8 秒，长回复的流式输出没有出现整段停顿；而 A 组有几轮首屏只要 900 毫秒，长回复照样断在中途。所以只测首屏，等于只测了一半。</p>
<h3>三天里最差的一天长什么样</h3>
<p>B 组也不是没有波动。第三天 23:30 那一轮，首字延迟抬到 2.4 秒，原因是上游线路在做例行维护，持续了大约四十分钟。区别在于这种波动有明确的结束时间，不像共享线路那样说不准什么时候好、什么时候坏。可预期本身就是一种体验。</p>

<h2>四、四个数字把这轮实验收口</h2>
<p>把九轮记录摊在表格里，不用图表也能看出结论。我用的四个指标都是脚本能自动采集的，不依赖主观打分，换个人复测也能得到接近的结果。</p>
<h3>首字延迟中位数比平均值可靠</h3>
<p>平均值会被那一两次十一秒的极端值拉偏，中位数更能反映日常体感。采集方式是在浏览器开发者工具的 Network 面板里看文档请求的 TTFB，或者用 curl 的 time_starttransfer 参数，取二十次的中位数。</p>
<h3>长回复完成率是硬指标</h3>
<p>分子是完整渲染到底的次数，分母是发起的总次数。低于 95% 就该警觉，低于 90% 会明显影响日常使用，因为你得为每次发送预留重发余量。</p>
<h3>重试次数和人工介入要一起记</h3>
<p>自动重试不算问题，人工介入才算。判断标准很简单：这一次失败需要你动手点一下、改一下或换个会话，就记一次人工介入。这个数字直接换算成工时。</p>

<h2>五、卡顿的根源常常不在带宽</h2>
<p>测完之后回头看，A 组那条线路的标称带宽其实比 B 组更高。也就是说，钱花在「更大的管道」上，未必能解决转圈的问题。真正拖慢体感的是下面三件事。</p>
<h3>地址在你不注意的时候漂移</h3>
<p>共享线路的出口地址是轮换的，同一账号上午从 A 段出、下午从 C 段出，平台侧看到的登录地记录一直在跳。每次跳变都可能带来一轮额外的校验环节，而这些环节是看不见的，只表现为「这次打开怎么特别慢」。固定地址的价值，一半在这里。</p>
<h3>并发队列的排队效应</h3>
<p>五个人共用一个出口，请求是排队的。单看每一个请求都不慢，五个叠在一起，最后一个人等的时间就是前面的总和。这种延迟和时间段强相关，所以才会出现「白天没事晚上崩」的规律。</p>
<h3>环境不一致带来的隐性等待</h3>
<p>出口在海外、系统时区却设成本地，语言偏好、日期格式、字体族都对不上，页面要额外做降级处理。这类等待单次只有一两百毫秒，但一次对话里请求几十个，累积起来就很可观。一个账号一套独立配置文件，本质上就是把这些参数一次配好、长期不动。</p>

<h2>常见问答</h2>
<h3>这套对照实验最少要跑几天？</h3>
<p>答：三天够看出趋势，七天更稳。关键是必须覆盖至少一个完整的工作日晚高峰，如果只跑周末，数据会偏乐观，因为周末的并发结构和工作日完全不同。</p>
<h3>没有脚本也能做吗？</h3>
<p>答：能，但要多花点耐心。手动记录时每轮固定发同一条提示词，用手机秒表掐首字出现的时间，一天记十次。样本少一些，方向性结论还是能得出的，只是别拿单次体验下判断。</p>
<h3>独立指纹具体指哪些参数？</h3>
<p>答：主要指时区、界面语言、Accept-Language 请求头、屏幕分辨率与缩放比例、以及字体渲染相关的设置。这些参数在同一个配置文件里保持一致即可，不需要逐项改写成某个特定值，重点是同一账号长期稳定。</p>
<h3>为什么换了独立出口，晚高峰还是会慢？</h3>
<p>答：独立出口解决的是排队和地址漂移两件事，解决不了上游线路拥塞。如果所在地区到出口的国际链路本身在晚间拥堵，换成独享地址一样会慢，这时候要看的是线路的回国路由和是否有中转节点。</p>
